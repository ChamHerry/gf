## 1. 实施结论

**当前问题**：GoFrame 框架有完善的项目结构规范和编码约定（目录结构、API 定义模式、Controller 模式、分层依赖规则），但缺少一个内置工具来自动检查项目是否符合这些规范。用户只能依赖人工 review 或外部 lint 工具，而外部工具不了解 GoFrame 特有约定。

**推荐实现路径**：在 `cmd/gf/internal/cmd/check/` 下创建独立的规则引擎包，基于 `go/parser` + `go/ast` 进行静态分析。引擎采用 Rule 接口模式（借鉴 `revive` 的设计），每个规则文件负责一类检查。通过 `cmd_check.go` 注册为 `gf check` 顶层命令。

**为什么这是最小风险方案**：
1. check 包完全独立，不修改任何现有代码（仅在 `gfcmd.go` 添加一行注册）。
2. 不引入 `golang.org/x/tools/go/analysis` 外部依赖，使用标准库 `go/ast` 即可。
3. 所有规则都是只读检查，不会修改项目文件。
4. 完全遵循现有 gf CLI 命令模式（struct + g.Meta + Index 方法），与 `cmd_fix.go` 模式一致。

**明确不做**：
1. 不做 go/analysis 框架集成（依赖太重）。
2. 不做 golangci-lint 插件（范围不同）。
3. 不做业务语义检查（超出静态分析范围）。
4. 不做 protobuf/gRPC 规范检查。
5. 不做自动修复（`gf fix` 已有此功能）。

**LLM 应从 T-001 开始执行。**

## 4. 目标方案

### 4.1 目标链路

```text
gf check [-p path] [-s/--strict] [--skip rule-id,...]
  -> cmd_check.go: cCheck.Index(ctx, in cCheckInput) (out *cCheckOutput, err error)
    -> check.NewEngine(projectRoot, options)
      -> engine.Scan()  // 扫描项目：gfile.ScanDir + go/parser.ParseFile
      -> engine.Run(ctx)  // 执行所有规则
        -> rules_dir.go:  CheckDirectoryStructure(project) []*Violation
        -> rules_api.go:  CheckAPIDefinitions(project) []*Violation
        -> rules_controller.go: CheckControllers(project) []*Violation
        -> rules_dao.go:  CheckDAOModel(project) []*Violation
        -> rules_layer.go: CheckLayerDependencies(project) []*Violation
        -> rules_config.go: CheckConfigurations(project) []*Violation
        -> rules_module.go: CheckModule(project) []*Violation
        -> rules_gen.go:  CheckGeneratedFiles(project) []*Violation
    -> engine.Report() -> check_result.go: Format(results) -> string
    -> mlog.Print(report)
    -> err = nil (pass) or err = gerror.NewCode(...) (violations found)
```

### 4.2 设计决策

| D-ID | 决策 | 理由 | 拒绝方案 | 影响任务 |
|---|---|---|---|---|
| D-001 | 采用 Rule 接口模式（借鉴 revive） | 可扩展、可测试、可单独注册 | go/analysis 分析器框架（依赖过重） | T-001 |
| D-002 | 使用标准库 `go/parser` + `go/ast` 进行代码分析 | 无额外依赖；genctrl 已证明此模式可行 | golang.org/x/tools/go/analysis | T-001,T-003,T-004 |
| D-003 | 规则分为 8 个文件（按检查类别） | 单一职责；易于维护和测试 | 单一大文件（可维护性差） | T-002~T-006 |
| D-004 | check 包放在 `internal/cmd/check/` | 与 genctrl/gendao/genservice 保持一致 | 放在 os/ 下（不在 cmd 模块范围） | T-001 |
| D-005 | 支持 text 和 JSON 两种输出格式 | text 用于人类阅读，JSON 用于 CI 集成 | 只支持 text | T-007 |
| D-006 | 通过 `hack/config.yaml` 配置 skip/strict | 与现有 gfcli 配置模式一致 | 单独的 .checkrc 文件 | T-007 |
| D-007 | 违规输出包含 rule ID + severity + file:line + suggestion | 提供可操作的修复建议 | 只输出错误描述 | T-001 |
| D-008 | 不修改项目文件（只读检查） | 安全；不会破坏用户代码 | 自动修复模式（gf fix 已有此功能） | 全部 |
| D-009 | 目录检查为第一优先级 | 目录结构是最基础的约定 | 先做代码检查（无法定位文件） | T-002 |
| D-010 | MVP 版本聚焦单仓项目，mono-repo 做基本检查 | mono-repo 检查逻辑复杂 | 完整 mono-repo 支持（T-009 只做基本验证） | T-002,T-009 |
