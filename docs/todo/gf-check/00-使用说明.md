# LLM 持续实施模板 — 使用说明

> 适用位置：`docs/todo/gf-check/`  
> 核心用途：让 LLM 能够在多轮会话中稳定读取状态、选择下一步、实施、验证、记录证据并恢复执行。  
> 设计原则：**任务可解析、状态可恢复、完成有证据、失败可回滚、范围可约束**。

---

## 1. 这个模板解决什么问题

普通实施方案适合人类阅读，但不一定适合 LLM 长周期执行。LLM 持续实施需要额外满足：

| 需求 | 模板约束 |
|---|---|
| 知道当前做到哪一步 | `README.md` 的 `LLM-STATE` 块记录当前任务、状态、下一步 |
| 能自动选择下一项任务 | `01-实施计划.md` 使用稳定 `T-###` 任务队列和依赖关系 |
| 不重复做已完成工作 | 每个任务有 `Status`、`Evidence`、`CompletedAt` |
| 不随意扩大范围 | 每个任务必须声明 `Files`、`Allowed Scope`、`Out of Scope` |
| 完成后能证明 | `02-实施状态与验证.md` 使用 `C-###` 命令记录和验收覆盖 |
| 失败后能恢复 | 每次失败记录 blocker、尝试、下一恢复动作 |
| 调研结论可复用 | `01-实施计划.md` 固化官方文档、GitHub 开源实现、版本约束和采用/拒绝理由 |
| 调用链分析可追踪 | `01-实施计划.md` 固化 subagent/GitNexus 调用链、数据流、配置流、错误流和影响面证据 |
| 每个任务实时校准 | `T-###` 执行前必须重新确认当前代码、候选文件、调用链和计划是否仍匹配 |
| 人类仍能审查 | README 保留摘要、风险、验收和交付物视图 |

## 2. 推荐目录结构

```text
docs/todo/gf-check/
├── 00-使用说明.md          # 模板说明
├── README.md               # LLM 执行控制台：状态、范围、下一步、验收
├── 01-实施计划.md          # LLM 任务队列：T-ID、依赖、步骤、验证、状态
├── 02-实施状态与验证.md    # 执行日志与验证证据：C-ID、结果、覆盖、VERDICT
└── 03-复盘与交接.md        # 决策、踩坑、回滚、维护和交接
```

> LLM 每次恢复执行时必须优先读取：`README.md` → `01-实施计划.md` → `02-实施状态与验证.md`。

## 3. LLM 执行协议

### 3.0 实施方案生成前（中大型任务必做）

本任务已完成的调研工作：

1. **官方文档调研**：已读取 GoFrame 项目结构文档、gen-ctrl/gen-dao/gen-service 文档、CLI 工具文档。
2. **GitHub 开源实现调研**：已调研 10+ 个相关开源项目（golangci-lint、revive、go-arch-lint、arch-go、depguard 等），记录可借鉴点和不采用原因。
3. **subagent + 代码索引深度分析**：已对 `cmd/gf` CLI 工具的命令注册链、代码生成子包结构、测试模式进行完整调用链分析。
4. **候选目标验证**：已对比多种实现方案（go/analysis vs 自定义检查器 vs 混合方案）。
5. **证据落盘**：调研和调用链结论已写入 `01-实施计划.md`。

### 3.1 每轮开始

LLM 开始实施前必须：

1. 读取 `README.md` 的 `LLM-STATE`。
2. 读取 `01-实施计划.md` 的任务队列。
3. 读取 `02-实施状态与验证.md` 的最新执行日志。
4. 选择第一个满足以下条件的任务：
   - `Status = todo` 或 `Status = blocked` 且有恢复动作；
   - 所有 `DependsOn` 都是 `done` 或 `skipped`；
   - 当前任务文件范围与用户授权范围一致；
   - 执行前实时校准通过：相关文件仍存在、调用链仍匹配、计划未落后于代码。
5. 如实时校准发现计划已过期，先更新 `01-实施计划.md §13` 和 `02-实施状态与验证.md §8`，再实施。
6. 将 `README.md` 的 `current_task` 更新为该任务。

### 3.2 每个任务实施中

每个 `T-###` 任务必须遵循：

```text
读取任务 -> 确认依赖 -> 实时校准代码/调用链 -> 限定文件范围 -> 实施最小切片 -> 运行该任务验证 -> 写执行日志 -> 更新任务状态
```

### 3.3 每轮结束

LLM 停止前必须更新：

1. `README.md`：`LLM-STATE`、当前状态、下一步。
2. `01-实施计划.md`：当前任务状态、证据、完成时间。
3. `02-实施状态与验证.md`：命令结果、失败原因、验收覆盖。

## 4. 状态枚举

### 4.1 功能状态

```text
todo | in_progress | blocked | partial | done | rolled_back | cancelled
```

### 4.2 任务状态

```text
todo | in_progress | blocked | done | skipped
```

### 4.3 验证状态

```text
not_run | pass | fail | partial | skipped
```

### 4.4 最终 VERDICT

```text
VERDICT: PASS
VERDICT: FAIL
VERDICT: PARTIAL
```

## 5. ID 规范

| 类型 | 格式 | 用途 |
|---|---|---|
| 需求 | `R-001` | 功能需求或验收需求 |
| 决策 | `D-001` | 关键技术/产品决策 |
| 任务 | `T-001` | LLM 可执行任务 |
| 命令 | `C-001` | 验证命令或检查 |
| 风险 | `RK-001` | 风险与回滚项 |
| 问题 | `B-001` | blocker 或失败项 |
| 后续 | `NEXT-001` | 非当前范围后续事项 |

---

## 6. 证据规范

"完成"必须绑定至少一种证据：

| 证据类型 | 示例 |
|---|---|
| 代码路径 | `cmd/gf/internal/cmd/check/check.go:runAll` |
| 测试文件 | `cmd/gf/internal/cmd/cmd_z_unit_check_test.go` |
| 命令 | `cd cmd/gf && go test ./internal/cmd/ -run Test_Check -count=1 -race` |
| CLI 输出 | `cd cmd/gf && go run . check -p testdata/check/sample-valid` |
| 官方文档 | `GoFrame official docs: project-structure` |
| GitHub 参考 | `mgechev/revive: borrowed Rule interface pattern, rejected go/analysis dependency` |
| subagent 分析 | `explore: command registration chain main.go → gfcmd.GetCommand → root.AddObject` |
